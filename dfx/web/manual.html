Project status

Early development build — not yet tested on real DVR evidence.
DFX has only been tested against synthetic test images, not drives or exports from real DVR/NVR recorders. Every built-in signature is unvalidated, and the Dahua DHAV offsets are partly unconfirmed. Do not use DFX for casework, or rely on its results, until it has been validated against known test data from real recorders.

This manual covers Build 1 (carving engine). These features are planned for later builds and are not in this version:

  • Dahua/Hikvision stream rebuilding and MP4 conversion with DVR timestamps
  • filesystem detection
  • DVR filesystem parsing (Hikvision HIKBTREE, Dahua)

What DFX does

DFX reads a DVR/NVR hard drive, or an image of one, read-only. It searches every byte for video using a library of signatures, which you can edit: patterns that say how an item starts and how to find where it ends.

Each item it finds is:

  • copied out to the case folder
  • hashed (MD5 and SHA-256)
  • logged with its exact location in the evidence
  • listed in an HTML report

It can:

  • Recover whole video files (MP4/MOV, AVI, MKV, WMV, FLV) from used or unallocated space.
  • Follow chains of DVR frames (Dahua DHAV style), recording the frame count, camera channel and first/last device time.
  • Carve any format you define yourself: header and footer, header and length field, or header and fixed size.

Quick start

  1. Home → New / Open Case: choose an empty case folder, then enter the case number, examiner and agency.
  2. Home → Image File or Physical Drive: choose the evidence.
  3. Home → Hash Evidence: wait for MD5 and SHA-256 to appear in the side panel.
  4. Clock Offset: create a record for the recorder and save its clock offset (optional, but needed to get actual times in the report).
  5. Carve: tick the signatures to use, and choose the DVR under DVR clock to add corrected times. For a first pass, tick Dry run to see what would be found without copying anything.
  6. Start Carve: progress, speed and time remaining show in the status bar.
  7. Results → Open Report.

Recorder clocks are often wrong. This tab measures how far the recorder's clock is from the actual time, saves that measurement in the case, and converts times in both directions:

  • DVR → actual: "the video says 9:15:30 PM, so when did it really happen?"
  • Actual → DVR: "the 911 call was at 9:11:18 PM, so where do I look on the recorder?"

It works like the DVR Tool phone app, with the measurements kept in the case file and printed on a worksheet.

Convention: Offset = DVR time − actual time. A positive offset means the DVR is fast (ahead), and is shown in red. A negative offset means it is slow (behind), and is shown in blue. Actual = DVR − offset.

Measuring the offset

  1. Choose the reference clock.
    • Workstation Clock (green, live): DFX shows what Windows is synced to (for example time.windows.com or your domain controller) and when it last synced. That information is saved with the measurement.
    • External Clock: use this when the workstation isn't trustworthy or you're working from a photo. Enter the reference time (for example from time.gov, a GPS clock, or a phone set to network time), press Set, and type the source.
  2. Set the time shown on the DVR. Type the date and time on the recorder's screen and press Set. The DVR clock then runs on its own. You can also press Copy reference to start from the reference time and adjust from there.
  3. Line it up to the second.
    1. Watch the recorder's screen.
    2. Press Pause the instant its seconds change.
    3. Use − / + until DFX shows the same second.
    4. Press Resume on the next change.
  4. Check the Offset line, for example DVR is 4 min 12 s fast (ahead), and add a note (how you read the time, photo number).
  5. Click Save Measurement, or Create New DVR using current offset if the recorder has no record yet.
A measurement is accurate to about ±1 second; that's the resolution of a recorder's on-screen clock. Photograph the recorder's screen next to the reference clock as supporting evidence.

Converting incident times

  1. Select the recorder in the Recorders list.
  2. Under Incident time, choose the direction:
    • Actual: you know the real time and want the DVR time.
    • DVR: you have the time from the video and want the actual time.
  3. Enter the date and time. Use − / + for single seconds.
  4. DFX shows the converted time, the offset used, how it was worked out, and any warnings.
  5. Type an event label (for example Suspect enters store) and click Log to save it to the worksheet and the case log.

If no recorder is selected, the conversion uses the live, unsaved offset. That's handy for a quick check, but it can't be logged.

Drift & daylight saving

Drift. A recorder's clock gains or loses time, often seconds a week. With one measurement, DFX assumes the offset never changed and says so on every conversion. Save a second measurement days later and DFX:

  • fits a drift rate (seconds per day)
  • estimates the offset at the exact time being converted
  • warns when the incident is outside the measured period and the drift had to be extrapolated

Daylight saving. If a DST change falls between the incident and the measurement (an incident in July measured in November, say), the offset may differ by one hour. What DFX does depends on the recorder's DST setting:

Recorder DST settingWhat DFX does
Auto DST offApplies the hour automatically and notes it. The recorder kept one clock, so local time moved but the recorder didn't.
Auto DST onApplies no hour correction, with a note to confirm the recorder actually changed its clock on the DST date.
Blank / UnknownWarns that the result may be off by one hour, and asks you to record the setting.

DST dates come from the examining workstation's time zone, so the workstation must be set to the recorder's time zone.

Testing a signature

  1. Open the signature in the editor (New or Edit / Copy).
  2. Click Test on File and choose a file whose contents you know: an export from the recorder, or a small test image.
  3. The results table shows each item's offset, length, status, frames, channels, first and last time, and notes. Nothing is copied. A test checks at most the first 2 GB and 100 items; the result says when it stopped early. Use a dry-run carve to test a whole drive.
  4. Change the fields and test again until every known item is found with the right length and nothing extra appears.
The test runs on what's in the editor, even before you save, so you can try changes safely.

Learning from samples

Learn from Samples drafts a signature from files you know are good: exports made by the recorder itself, or byte ranges you mark in the Hex tab.

  1. Click Learn from Samples, then Add Files…. Add 3 or more samples of one format, ideally from different channels and different times. With fewer than 3, DFX can't tell fixed bytes from bytes that just happen to match, and says so.
  2. Optionally type a signature ID and name, then click Run Learner.
  3. Read the Findings. Every finding says what backs it, for example "equals the distance to the next frame in 93 of 93 frames".
  4. Check the Self-test. Each sample was planted in random data and carved back with the draft. Every row must say exact, and there should be no extra hits in the random data.
  5. Click Open in Editor to review, adjust and save the draft. It is saved unvalidated; validate it on real evidence before relying on it (see Validating signatures).
The learner looks forHow
HeaderBytes every sample (or every frame) starts with. Bytes that differ become ??. Bytes inside a learned length or timestamp field always become ??, even if the samples agree, so a header can't be tied to small files.
Frame markerThe header repeating inside every sample, always starting at byte 0: a stream of frames (like Dahua DHAV). The shortest marker that explains the frames is used, so a frame-type byte (keyframe vs. other frames) isn't mistaken for part of the marker.
Length fieldA 1-, 2-, 4- or 8-byte number in each frame (or file) header, either byte order, that equals the distance to the next frame (or the file size), plus or minus a constant (adjust). It must hold for at least 90% of frames.
Footer2 or 4 bytes at the same distance from the end of every frame or file; bytes after it become bytes after footer.
Timestamp (candidate)A field that decodes to plausible Dahua-packed or Unix times that never go backwards inside a sample. Check it against the times you recorded.
Channel (suggestion)A small number that is constant inside each sample but differs between samples. Confirm it with samples from channels you know.

On large samples, fields are checked on the first 2,000 frames of each sample (the findings say so). Every run is recorded in the case log.

When you don't need a learned signature. If the samples are standard MP4, AVI, MKV or ASF files (Dahua's .asf exports, for example), the learner says so in a green box and names the built-in signature that already recovers them with exact lengths. Use that one.

Frames after a file header. Some exports start with a file header and then the recorder's frames. The learner finds frame streams that start within the first 4 KB and describes the frames (what the DVR's drive holds), not the export's header.

Learner messageWhat it means
Only N sample(s)A caution, not an error. With fewer than 3, a byte that matches by coincidence can end up in the header.
No length field or footer foundNothing in the samples tells where an item ends, so lengths can only be estimated. Check whether the green box names a built-in signature.
Self-test: every sample was found at its start…The estimated mode worked as well as it can; lengths aren't expected to match exactly.
Self-test failedThe draft didn't find every sample. Don't use it; look at the self-test table and the findings.

Building a signature in hex

  1. Find a known header, such as 44 48 41 56.
  2. Select the first bytes of the frame or file (2 to 32 bytes) and click Use as Header. They're outlined in green.
  3. Select the bytes you think hold the size (1, 2, 4 or 8) and click Length Field. They turn blue. In Signature being built, choose the byte order and adjust; DFX shows the value and where the next item would start.
  4. Click Follow Length. DFX jumps there and tells you whether the header is really there ("Length field checks out"). Keep clicking to walk from frame to frame.
  5. Optionally select footer bytes and click Use as Footer.
  6. Tick a stream of frames for DVR frame streams (frame_chain), or untick it for whole files (header_length).
  7. Click Open in Editor, review it, and use Test on File before saving.

Length judge (mediacarve)

The built-in MP4/MOV, AVI and MKV/WebM signatures don't guess where a file ends: they ask mediacarve (by Alexis Brignoni, included in DFX), which walks each format's own structure. Every item records how its length was known, in the Length is column:

LabelMeaningCan it hide later hits?
headerThe file's own header recorded the length.Yes
parsedThe length came from walking the file's structure to its end.Yes
cappedThe end was not confirmed. The length is a ceiling, not a fact: truncated, cut at the next header, or overwritten.Never

Overwritten recordings. On a DVR drive, the end of an old recording is often overwritten by a newer one, but the old file's header still declares its full original length. If another valid video header starts inside that declared length, DFX cuts the old file there, labels it capped with the note "probably overwritten", and recovers the newer file separately.

mediacarve knows nothing of DVR formats (Dahua DHAV, Hikvision IMKH); those keep DFX's own modes. The mediacarve version used is recorded on every report.

A header hit that falls inside an item whose end is known (footer found, length field, box walk, frame chain) is skipped, so the 39 inner frames of a 40-frame chain aren't carved again. Items whose end is only estimated (max size, or "footer missing → maxsize") never hide later hits, so a real file inside a guessed range is still found. Overlapping header candidates are all checked.

The report

report.html contains:

  • Warnings at the top: early-development build, evidence not hashed, unvalidated signatures used, read problems (short reads or unreadable areas, with offsets), scan incomplete, canceled scan, dry run.
  • Case: number, examiner, agency, description.
  • Evidence: path, type, size, sector size, MD5/SHA-256 with the time they were calculated, and a read-only statement.
  • Scan: range, start and finish times (UTC), elapsed time, bytes scanned, items, rejected hits, alignment, signature set SHA-256.
  • Signatures: each one used, its mode, header, footer, validation state and item count.
  • Items: offset (hex and decimal), length, status, frames, channel, first and last device time, file path, MD5, SHA-256, notes.
  • Signature definitions used: the full JSON, so the scan can be repeated exactly.

Cancel & resume

DFX saves a checkpoint every 15 seconds and when a scan stops. To continue a run:

  1. Open the same case and select the same evidence.
  2. Carve tab → Resume Run → choose the run.
  3. The scan continues from the checkpoint and adds to the same carve_log.csv.

Resume is crash-safe:

  • Items already in carve_log.csv are never carved or logged twice, even when the last checkpoint is older than the last item.
  • Each file is written as .part and renamed only after its log row is written. After a crash, a .part whose row exists is checked against its logged SHA-256 and finished; an unlogged .part is deleted. Both are recorded in the case log.
  • The run continues with its original range, dry-run, alignment, chunk and max-items settings.

Resume refuses to continue if:

  • the evidence size doesn't match, or
  • the signature definitions changed since the checkpoint (DFX compares their SHA-256).

In either case, start a new run instead.

Validating signatures

A signature should be marked Validated only when you can show it works on data whose contents you already know. A suggested procedure:

  1. Use a recorder you control, of the same make and family. Set its clock from NTP and note the time.
  2. Record known events: point a camera at a screen showing an NTP-synced clock, and record set windows (for example channel 1, 10:00:00–10:05:00).
  3. Export the same clips with the recorder's own software.
  4. Image the drive through a write blocker and hash it.
  5. Run DFX on the image with only the signature being validated.
  6. Confirm that:
    • every known recording was found, with the right channel and device times
    • the carved data matches byte-for-byte where an exported copy exists
    • there are no unexplained extra items
  7. Record the DFX version, signature JSON, image hash and results (the Forensic Tool Validator can hold this), then tick Validated and note the test in Notes.
  8. Repeat after any change to the signature or any new DFX version.

Evidence handling

  • DFX opens every source read-only. There is no code path that writes to the source.
  • Still use a hardware write blocker for physical drives, and prefer working from a verified image.
  • Hash the evidence in DFX and compare it with your acquisition hash before carving.
  • Keep the case folder on a different drive from the evidence.
  • Some DVRs format drives with a 4096-byte sector size. DFX reads the sector size from Windows and shows it on the report.

Device times

A DVR's clock is often wrong. Times shown for frame chains are decoded exactly as the recorder wrote them, with no time-zone correction. To get actual times, measure the recorder's offset in the Clock Offset tab and choose that recorder under DVR clock on the Carve tab. The report then lists both the device time and the corrected time. DFX never changes the device times themselves.

Thousands of tiny or junk itemsThe header is too short or too common. Lengthen the header, set a sensible min size, use Sector-aligned only, or use header_length/frame_chain instead of header_maxsize.

FAQ

Does DFX convert DVR video to MP4?
Not in this build. It copies out the original data. Conversion with DVR timestamps is planned for Build 3.

Does DFX read the DVR's own filesystem (file list, deleted entries)?
Not yet. This build carves by signature across the whole drive. Filesystem parsing is planned for Builds 4–5.

Can I share signatures?
Yes. Use Export JSON. The person who receives them should treat them as unvalidated until they test them on their own data.

Where are settings kept?
%APPDATA%\DFX: settings.json (last case) and signatures\ (user signatures).
